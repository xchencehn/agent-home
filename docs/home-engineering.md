# Agent Home：项目自有的持久工作环境

> **一句话结论：** Agent Home 是由项目或组织拥有、独立于具体模型与 Harness 的持久工作环境；
> Agent 可以更换，Harness 可以升级，但项目的目标、知识、状态、资源、权限、证据和责任必须持续积累。

## 现状

当前仓库把 Agent Home 实现成一份可直接克隆的项目模板。用户改好目录名，在仓库内启动 Codex、
Claude Code 或其他兼容工具，项目规则、Skill 和工作状态就随 Git 一起到达，不需要额外安装插件。

仓库中的信息各有明确归属：

| 内容 | 当前载体 |
| --- | --- |
| 项目身份、目标与稳定范围 | `PROJECT.md` |
| 始终生效的工作规则 | `AGENTS.md` |
| 可复用的项目工作能力 | `.agents/skills/` |
| 跨会话的长期工作状态 | `tasks/` |
| 面向人的稳定理解 | `docs/`、`reports/` |
| 机器可复核的边界 | `tests/` |

当前实现还用结构化导航避免把“继续处理”当作下一步。下面三行来自真实的
[`workflow.py`](../.agents/skills/task-loop-run/scripts/workflow.py)：

```python
"candidates": [],
"next_action": None,  # 关键：任何时刻只选择一个当前动作。
"blockers": [],
```

这些机制是 Agent Home 在本仓的参考实现，不是 Agent Home 的完整定义。

## 问题本身

**项目能力如果只存在于某次会话、某个模型或某个厂商工具中，就不真正属于项目。**

模型和 Harness 会快速进步：推理套路可能进入模型，工具调用、上下文压缩、规划和多 Agent 编排可能成为
平台默认能力。围绕某一代工具搭建的通用脚手架，迟早可能被更底层的平台吸收。

但项目仍有一类能力不能被通用平台替项目决定：为什么做、什么事实可信、哪些决策已经做过、能使用哪些
资源、谁有权发布、什么证据足以验收，以及面对未知时应该怎样继续探索。这些能力绑定项目语义、组织责任
和真实世界状态，必须由项目长期掌握。

最小失败过程通常是：

```text
会话 A 完成了一半工作，关键理由只留在聊天中
→ 更换 Agent、模型或工具
→ 会话 B 只能重新猜测目标、边界、证据和下一步
```

真正丢失的不是几段文字，而是项目连续工作的能力。

## 深度剖析

### Model、Harness 与 Home 是三个不同层次

最简洁的区分是：

> 模型提供智力，Harness 提供行动能力，Home 提供项目工作能力。

| 层次 | 负责什么 | 不应假设它天然拥有什么 |
| --- | --- | --- |
| Model | 理解、推理与生成 | 当前项目事实、权限、责任和长期历史 |
| Harness | 上下文组织、工具调用与行动循环 | 项目对目标、证据和资源的最终定义权 |
| Home | 项目持续存在的规则、知识、状态与责任 | 某个固定模型或厂商实现 |

一次实际工作的 Agent 实例可以理解为：

```text
Agent instance
= Model
+ Runtime Harness
+ Current Goal and State
+ Work Environment
+ Authority
```

同一个 Model 和 Harness 进入不同 Home，会获得不同的项目工作能力。

### “项目拥有”指控制权，而不是全部自研

厂商可以提供存储、任务、记忆、Skill、资源连接和治理机制。项目拥有 Home，不意味着排斥厂商，也不要求
底层软件全部自研；它意味着项目能够控制并迁移以下内容：

- 语义：目标、术语、事实与历史决策由谁定义；
- 状态：换会话、换模型、换 Harness 后能否恢复；
- 权限：谁可以读、写、发布、审批和回滚；
- 证据：什么能够证明结果，什么仍然没有被证明；
- 责任：最终接受、风险和外部影响由谁承担。

因此，Home 可以存储在 Git、数据库、对象存储或企业系统里。判断标准不是物理目录，而是项目是否掌握
语义、生命周期、迁移和责任。

### 常见替代物只覆盖了 Home 的一部分

| 替代方式 | 能解决什么 | 缺少什么 |
| --- | --- | --- |
| 更长的系统提示词 | 稳定规则 | 工作状态、资源、证据与恢复 |
| 模型记忆 | 部分跨会话信息 | 项目可审计的所有权、版本和责任边界 |
| Harness 原生任务 | 通用执行与恢复 | 项目自己的语义、验收和迁移控制 |
| 插件 | 分发通用能力 | 克隆项目时并不会自然带走安装、身份和缓存状态 |
| 完整聊天或命令流水 | 保留原始过程 | 难以区分事实、结论、噪声和当前路线 |

Agent Home 不是这些机制的竞争者，而是组织它们的项目层。

## 方案

### Home 保存七类项目能力

一个完整的 Agent Home 至少应覆盖七类能力：

| 能力 | 回答的问题 |
| --- | --- |
| 目标与边界 | 为什么做、做到什么程度、哪里不能越界 |
| 知识与技能 | 项目知道什么、有哪些可重复的方法 |
| 持久工作状态 | 已经做到哪里、验证或否定了哪些方向 |
| 资源与能力 | 可以使用哪些代码仓、设备、系统和人员 |
| 权限与治理 | 谁可以读取、修改、发布、审批和回滚 |
| 证据与验收 | 什么事实支撑结论，什么仍然没有被证明 |
| 探索与行动导航 | 面对未知时怎样澄清、试探、选择和转向 |

这七类能力共同构成“项目工作能力”。只有规则没有状态，无法恢复；只有状态没有证据，无法相信；只有工具
没有权限，无法负责；只有计划没有探索导航，遇到未知就会僵化。

### 当前仓库选择最简单的可迁移实现

本仓把 Git 仓库作为 Home 的分发和持久化载体：

```bash
git clone https://github.com/xchencehn/agent-home.git my-project
cd my-project
codex  # 或 claude
```

Task/Loop/Run、设计梳理、`next_action` 和证据检查点只是这份实现目前采用的机制：

- Task 保存长期目标；Loop 保存一个可证伪方向；Run 保存一次执行结果；
- 设计梳理只在目标、范围、验收或转向条件仍不清楚时触发；
- `next_action` 从当前行动前沿只选择一个有完成条件的动作，并在新证据到来后重算；
- 证据检查点只保存会改变路线、支撑结论或用于恢复的事实。

它们不等于 Agent Home 本身，也不因为被实现就自动证明有效。它们是当前可运行、可替换、应继续用强基线
检验的参考方案。

### Home 的仪式成本必须与工作复杂度相称

简单请求直接完成，不创建 Task。只有长期、多阶段、需要假设验证或跨会话恢复的工作，才启用持久记录。
Home 的目的不是让 Agent 花更多时间管理记录，而是防止项目能力随会话结束而消失。

当前仓库用下面的命令验证发现入口、简中界面、生命周期、同层活动约束、证据引用和 Run 合同不可变性：

```bash
python -m unittest discover -s tests -v
```

机器测试只能证明实现满足当前契约，不能证明这套机制必然比所有基线更高效。效果、成本和适用范围仍应在
真实长期任务中持续比较。

## 小结

| 容易混淆的理解 | 我们的 Agent Home 理念 |
| --- | --- |
| Home 是某个插件或工具 | Home 是项目自有、可迁移的工作环境 |
| 更强模型会解决全部问题 | 通用能力会升级，项目语义与责任仍需项目掌握 |
| Harness 就是 Home | Harness 负责行动，Home 保存项目工作能力 |
| Task/Loop/Run 就是 Home | 它只是当前持久状态的参考实现 |
| 记录越多越可靠 | 只保留恢复、判断和责任真正需要的最小真值 |

最终愿景可以压缩成两句话：

> 不要把项目能力塞进某一个 Agent，要把它建设在 Agent Home 中。

> Agent 可以更换，Harness 可以升级，Home 持续积累。
