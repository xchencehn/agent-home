# Home Engineering：把仓库变成 Agent 的工作家园

> **一句话结论：** Agent Home 不是需要安装的插件，也不是一段更长的提示词；它是一个可克隆、可改名、
> 可恢复、可验证的仓库，让 Agent 换机器、换工具、换会话后仍能从同一份工程真值继续工作。

## 现状

当前 Agent Home 已经是一份零安装仓库模板：用户克隆仓库、指定新目录名，再在目录内启动 Codex 或
Claude Code，项目规则、工作流和恢复协议便随 Git 一起到达。

根规则在 [AGENTS.md](../AGENTS.md) 中给出了最小管理模型：

```md
- Task 管长期目标，Loop 管一个可证伪方向或阶段，Run 管一次具体执行结果。
- 目标、范围或验收仍模糊时使用 `design-grill`，不要带着迷雾直接实施。
- Task、Loop 或 Run 打开、恢复、遇到关键结果或阻塞时使用 `next-action`，只选择一个当前可执行动作。
- 只有会改变下一步、支撑结论或用于恢复与交接的事实才使用 `evidence-checkpoint`。
```

这里的关键不在目录层级，而在职责分离：目标、假设、执行、事实和下一步不能混成一段聊天摘要。

机器恢复真值由
[workflow.py](../.agents/skills/task-loop-run/scripts/workflow.py) 创建和校验。导航状态的真实源码如下：

```python
def navigation(summary, clarity, completion_conditions=None):
    return {
        "destination": {
            "summary": summary,
            "clarity": clarity,
            "completion_conditions": completion_conditions or [],
        },
        "known_refs": [],
        "questions": [],
        "fog": [],
        "out_of_scope": [],
        "candidates": [],
        "next_action": None,  # 关键：任何时刻只选择一个当前动作。
        "blockers": [],
    }
```

这些英文键是稳定协议字段，不是面向人的叙述文本。它们把目标、事实、问题、迷雾、候选、阻塞和选中的
下一步分开，避免 Agent 用一句“继续处理”掩盖真实状态。

## 问题本身

真正的问题是：**普通仓库只保存代码，普通聊天只保存当前会话，而长期 Agent 工作需要一个跨会话的工程
家园。** 如果这个家园依赖插件安装、个人配置或聊天记忆，它就无法随项目一起迁移；如果它只包含一份
`AGENTS.md`，又无法恢复正在验证的方向、执行合同和决定性证据。

最小复现非常简单：

```text
会话 A：分析了三个方向，排除两个，第三个完成一半。
会话结束：结论、证据边界和真正下一步只存在于聊天中。
会话 B：重新读取仓库，只看到源码，不知道为何排除前两个方向。
结果：重复调查、误走旧路，或把过期待办当成当前路线。
```

更隐蔽的变体不是“完全丢失”，而是“看似恢复”。一个陈旧的 `next_action`、一份没有来源的总结或一次成功
退出的命令，都可能让新会话相信工作已经收敛，但实际上证据、目标或环境早已变化。

## 深度剖析

### 根因是五类真值没有共同落在项目里

一个可迁移的 Agent 工作家园至少要保存五类不同真值：

| 真值 | 回答的问题 | 本仓位置 |
| --- | --- | --- |
| 项目身份 | 这是哪个项目，要达到什么目标 | `PROJECT.md` |
| 稳定规则 | 始终应该怎样工作 | `AGENTS.md` |
| 可复用能力 | 某类工作应该怎样执行 | `.agents/skills/` |
| 当前进度 | 现在位于哪个目标、假设和执行边界 | `tasks/` |
| 可复核事实 | 哪些证据支撑结论，机器怎样检查 | `checkpoints.jsonl`、`result.json`、`tests/` |

只缺一层，Agent 就会用聊天上下文补洞。聊天上下文适合交流，不适合作为工程真值：它不可稳定寻址、难以
做结构校验，也不会天然跟随 Git 克隆。

### 三层、四文件、一个下一步是刻意压缩后的结果

这套模型用三个层级而不是一棵任意深的工作树：

- Task 回答“长期要达到什么”；
- Loop 回答“当前在验证哪个可证伪方向”；
- Run 回答“这一次具体做什么，得到什么结果”。

每个 Run 只保留四个核心恢复文件：

| 文件 | 性质 | 作用 |
| --- | --- | --- |
| `contract.json` | 打开后不可变 | 防止执行后篡改目标来制造通过 |
| `state.json` | 可变 | 保存当前恢复位置、合同摘要和导航状态 |
| `checkpoints.jsonl` | 只追加 | 保存改变决策、支撑结论或用于恢复的事实 |
| `result.json` | 终态提案 | 汇总结论、限制和检查点引用 |

导航层只允许一个 `next_action`，因为下一步是当前行动前沿中被选中的一个成员，而不是未来待办列表。其他
可能方向仍可作为候选；已知依赖进入阻塞；还说不清的问题留在迷雾中。每次观察到新结果后重新计算，形成
`定向 → 分层 → 选步 → 执行 → 观察 → 重算` 的闭环。

### 常见替代方案分别丢失了不同能力

| 方案 | 思路 | 卡住的位置 |
| --- | --- | --- |
| 插件作为 Home | 把协议和运行时装到工具里 | 出现安装、发现、版本、缓存和项目身份问题，克隆仓库并不能带走完整 Home |
| 只有根提示词 | 用一份规则约束 Agent | 能说明“应该怎样做”，不能恢复“已经做到哪里” |
| 保存完整聊天或命令流水 | 任何信息都不丢 | 信号被噪声淹没，无法区分事实、尝试、结论和当前路线 |
| 每个请求强制建状态机 | 所有工作都结构化 | 一步任务也承担治理成本，协议反过来成为主要工作 |
| 仓库原生 Home Engineering | 规则、Skill、状态和验证都进 Git | 既可迁移，也能按工作复杂度选择是否启用持久协议 |

因此，Home Engineering 的“Engineering”指的不是多写几份 Markdown，而是同时具备可执行初始化、结构
校验、不可变边界、只追加证据和端到端测试。没有机器判据的约定只能算写作习惯，不能算工程协议。

## 方案

### 仓库就是分发单元

最短使用路径只有三步：

```bash
git clone https://github.com/xchencehn/agent-home.git my-project
cd my-project
codex  # 或 claude
```

`bootstrap-project` 使用目录名和用户目标完成首次项目化；Codex 从 `.agents/skills/` 发现工作流，Claude
Code 通过 `.claude/skills/` 的薄包装层读取同一份真值。仓库不要求插件市场、安装缓存或个人机器路径。

### 五个 Skill 组成最小能力面

| Skill | 负责 | 不负责 |
| --- | --- | --- |
| `bootstrap-project` | 把模板变成具体项目 | 为每个请求强制创建 Task |
| `task-loop-run` | 打开、恢复和关闭持久工作层级 | 代替技术判断 |
| `design-grill` | 在实施前澄清范围、风险和证伪边界 | 保存原始执行日志 |
| `next-action` | 从当前行动前沿选择一个动作 | 生成一整条臆测路线 |
| `evidence-checkpoint` | 保存决定性事实及其限制 | 记录每次读取和重试 |

Skill 触发描述常驻 Agent 初始上下文，完整正文只在命中时加载。这样既能自动发现，又不会把所有工作流
同时塞进上下文。

### 结构真值必须能被机器拒绝

`workflow.py` 不仅创建目录，还会拒绝越界路径、同层重复活动记录、迷雾状态下的直接实施、重复或失配的
检查点，以及 Run 打开后被改写的合同。合同完整性由 `state.json` 中保存的 SHA-256 摘要校验。

[模板契约测试](../tests/test_template_contract.py) 对不可变合同的验证使用了真实前后字节比较，并进一步制造
改写后要求校验失败：

```python
self.assertEqual(contract.read_bytes(), original_contract)
changed_contract = json.loads(contract.read_text())
changed_contract["objective"] = "执行后被改写"
contract.write_text(json.dumps(changed_contract))
self.run_workflow(root, "check", run, expected=2)
```

这条测试表达了 Home Engineering 的核心态度：记录不是装饰。若协议声称合同不可变，机器就必须能够发现
改写；若证据声称支撑结论，结果就必须引用真实存在的检查点。

### 仪式成本必须与工作复杂度成比例

简单请求直接完成，不创建 Task。只有需要多步验证、跨会话恢复、假设分支或交接时，才启用
Task/Loop/Run。即使启用，也不生成状态视图、会话全文、签名链、晋升状态或空证据文件。

扩展项目时继续遵守相同分层：

- 始终生效的规则进 `AGENTS.md`；
- 项目身份和稳定范围进 `PROJECT.md`；
- 可重复条件工作流进新的 Skill；
- 当前长期工作进 `tasks/`；
- 面向人的稳定理解进 `docs/`；
- 可机器复核的约束进 `tests/`。

## 小结

| 维度 | 容易滑向的旧方式 | Home Engineering |
| --- | --- | --- |
| 分发 | 安装插件并同步个人配置 | 克隆仓库即获得完整工作家园 |
| 项目真值 | 分散在聊天、缓存和机器目录 | 随 Git 一起迁移 |
| 长期工作 | 一串没有边界的待办 | Task 管目标，Loop 管假设，Run 管执行结果 |
| 模糊问题 | 带着未知项直接实现 | 先设计梳理，再冻结可证伪方向 |
| 下一步 | 预写未来动作链 | 每次观察后只重算一个当前动作 |
| 证据 | 保存全部流水或只写结论 | 只追加决定性事实，并明确来源与限制 |
| 正确性 | 靠 Agent 自觉遵守文档 | 用脚本和测试拒绝结构性错误 |

可带走的方法论是：**把 Agent 的工作环境当成代码一样工程化——能够克隆、能够恢复、能够验证，同时只为
真正复杂的工作支付管理成本。**
